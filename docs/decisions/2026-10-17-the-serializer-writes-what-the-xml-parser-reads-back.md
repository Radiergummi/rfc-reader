# The serializer writes what the XML parser reads back

*Recorded 17 October 2026 from ARCHITECTURE.md (#756); decided with #315, #683 and #686.*

The XML parser indexes `<reference>` anchors first, in every `<references>` wherever it sits, not only `<back>`'s, so `<xref target="QUIC-TRANSPORT">` becomes `.document(RFC9000)`. XML from elsewhere can hold a list in a chapter or in `<middle>`, and so could a converted legacy document until #315: the serializer now lifts every bibliography outside the back into it, keeping its anchor, number and name, in document order before the back's sections, and wraps a list's own entries in a nested list named after it where it also holds lists of its own, which is the one shape the schema accepts there. A numbered section that follows the last bibliography goes into the back with it and keeps a section's `pn`, and the parser reads a `<back>` section by its `pn`, by its place only where it has none, so that section is not announced as an appendix (#683). What the serializer writes for a legacy document is a fixed point: parsed and written again with the same options, it is the same bytes, so a patched document changes only where its patch does (`SerializerRoundTripTests`; over the corpus, every document since #686). That holds because the legacy parser builds what reading the XML gives, not because the serializer copies the XML parser's rules: titles with their whitespace collapsed, a URL into the RFC series as a citation (in `InlineLinker`, which both parsers run), a definition's term linked like its text. Where RFCXML can only say something one way, the serializer says it so: a label composed from the document, written against an entry whose tag is another, names the document in the xref's words, which the parser reads as the document's label. The text parser, like the XML parser, indexes the bibliography first, here the `[RFC2119]`-style entries in the References section, then linkifies `[Anchor]`, `RFC 1234`, `Section 4.2 of [RFC9110]`, `Section 3` (only if that section exists) and URLs in prose.
