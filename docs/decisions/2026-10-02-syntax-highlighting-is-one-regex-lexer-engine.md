# Syntax highlighting is one regex lexer engine

*Decided October 2026 (design in `docs/superpowers/specs/2026-10-02-syntax-highlighting-design.md`, plan in `docs/superpowers/plans/2026-10-02-syntax-highlighting.md`).* Source code is highlighted by one regex state-machine engine in RFCKit, `Lexer`, as Pygments, Rouge and Chroma lex: named states, each an ordered list of rules, and a language is a table of them (`JSONLexer`, `XMLLexer`). Where a table cannot say what a language needs, a small highlighter is written on the engine: `HTTPMessageHighlighter` splits a block into messages and each into a head, lexed by a table, and a body, lexed as its `Content-Type` says. `Lexers` is the one place a block's type names a language, by its canonical name or, failing that, by its structured suffix (`application/problem+json` is JSON). JSON, XML and HTTP messages are the first slice; further languages are tables on the same engine.

What the code in RFCs is decided against the alternatives. Over the 9,835 RFCXML documents, counted on 2 October 2026, the most common `<sourcecode>` types are `test-vectors` (1,304), `json` (1,050), untyped (1,257), `pseudocode` (673), `http-message` (503), `asn.1` (482), `xml` (398), `yangtree` (388), `abnf` (292), `yang` (272), `cddl` (252), `sdp` (236), `xdr` (196), `rbnf` (131), `cbor-diag` (127), `tls-presentation` (111), `abnf9110` (102) and `c` (96): more than half are IETF formats few highlighters know, and blocks are usually fragments. JavaScript highlighters (Highlightr, HighlightSwift) are ruled out by VISION.md, and JavaScriptCore does not exist on Linux, where RFCKit is tested. Tree-sitter is the fastest and builds on Linux, but mature grammars exist only for JSON, XML, C, Python and YAML; for ABNF, ASN.1, YANG, CDDL, XDR and SDP there are hobby grammars of a handful of stars or none, and a grammar expects a whole file, so a fragment becomes `ERROR` nodes. TextMate grammars have the widest ecosystem but no maintained Swift engine, and depend on Oniguruma's semantics. A regex lexer has no notion of a whole file, and its definitions can be translated from Pygments (BSD) and Chroma (MIT). Highlighting is lexical; where a feature needs structure, such as ABNF's rule links (#185), a dedicated parser serves it.

The engine compiles each state to one alternation, `(rule0)|(rule1)|…`, and searches forward from the current position: the first rule that matches at the earliest position wins, and the characters before it, which no rule matched, are plain. So it never fails, and the tokens cover a block exactly once. A state other than the root that meets a character it cannot match has lost its place, and at the next newline lexing starts again from the root, as Pygments recovers. Matching uses transparent and non-anchoring bounds, so a lookbehind sees the characters before the position and `^` matches only where a line starts. A rule whose groups nest, or that refers back to a group (which the alternation renumbers), is refused when its lexer is built; a rule that could match nothing must change state, and states that only trade places on lookaheads give up a character after eight such steps. Repetitions are possessive wherever that does not change what matches, and a block over 65,536 UTF-16 code units is not highlighted. A JSON string or XML value ends at its line, so one left open colors nothing after it, except across an RFC 8792 fold — a backslash at the end of the line — which the corpus showed is how most long strings in RFCs are set, and which the reader shows as published where unfolding would not fit.

The reader shows it as `Rendition.styled`, registered with the artwork renderers (`SyntaxPresentation`). Highlighting is always on and outside the presentation choices: "Draw diagrams" and "Show as Text" are about drawings, and code has no other presentation to switch to. A highlighted block is not a figure — no menu item to switch it, no long-press figure item on iOS, no centering — and VoiceOver reads it as code, never as a diagram. Tokens are lexed from the text shown, so a block unfolded in a wide column is highlighted as one folded in a narrow one. Colors come from `SyntaxTheme.standard`: dynamic, so dark mode is a redraw and print's light appearance needs no rebuild, and each at 4.5:1 or more against the verbatim card in both appearances, which the system's secondary label color, about 4:1, is not. Plain tokens keep the body color of their context. The theme is a value so that pickers or a color-blind variant can hand the builder another one; when it becomes a preference it joins `ReadingStyle`, which keys the preview cache.

The lexers adapted from Chroma, itself converted from Pygments, carry both projects' notices: `THIRD_PARTY_NOTICES` at the repository root, shown in the About panel on macOS and in Acknowledgements, from the library's menu, on iOS. `Acknowledgements.text` in RFCReaderKit is that file word for word, and a test holds them the same.

Measured on 3 October 2026 (`make benchmark`, p50 wall clock, against a baseline taken before any highlighting code): the build of RFC 8727, whose 53 KB JSON block is the corpus's largest, went from 30 to 77 ms, and RFC 8927's, mostly JSON, from 20 to 34 ms; RFC 9110 and RFC 9000 stayed within noise. Lexing RFC 8727's blocks alone takes 21 ms; the rest is the builder setting a color per token. That is over the 10% the plan allowed, and is open.
