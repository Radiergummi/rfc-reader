# A translated document is a second build of a translated model

*Decided 17 October 2026 (issue #749).*

A reader who wants an RFC in their own language asks for it with **Translate** in the More menu, beside Original Text, on both platforms. The Translation framework translates it on the device. The text the reader shows is then the translation, until **Show Original** in the header, or Translate again, brings back the English. Translate is offered only to a reader with a language other than English among their preferred languages, and translates into the first of those (`DocumentTranslation.target`).

**What a translated document is.** It is the original `RFCDocument` with its prose replaced, and nothing else: the same sections, blocks and anchors. So it is built by the same `DocumentTextBuilder`, off the main actor, and installed as any build is. The contents, deep links, reading positions and Find work on it unchanged, and switching between the two keeps the reader's place by anchor. Nothing below the builder knows about translation. `DocumentTranslation` makes the model, `TranslatedDocument` carries it with its labels, and `BuiltDocument.translation` says a build is one.

**What is translated** is what a reader reads as prose: paragraphs, list items, definitions and their terms, table cells, quotations, asides, section titles, and figure and table titles. **What is not** is what is set as typed, or is a name: artwork, source code, grammars, the bibliography, the index, and the header (title, authors, status). A run with a superscript or subscript is not translated either, because plain text runs 2 and 32 into 232.

**Links survive by their words.** Each run of prose is sent as plain text, so its grammar is the translation's own, with each cross reference written as its label. Afterwards each reference, each piece of inline code and each web link is linked again where its words turn up in the translation (`Relinking`). That is as they were, as "RFC 9110" and "[HTTP]" usually come back. A reference written in words, "Section 4", is also found by that label's own translation. One found neither way is plain text in the translated paragraph, not a link on the wrong words. Emphasis is lost. Translating inline by inline was rejected because it breaks the grammar. The framework's `SkipTranslationAttribute` on an attributed request is the alternative to measure if links are lost too often.

**The builder's own words are translated too**: "Abstract", "Note", the figure, table and appendix labels, and the backlink captions (`DocumentLabels`), by the same session as the prose. The decision that the body is not localized was against a body in two languages, and English labels beside translated prose would be one. A label that names a numbered thing is asked for with a number, "Figure 1", so it is translated as a label, and the label is what is left beside the number. A language that writes the number on the other side keeps the English label. The contents panel still says "Appendix" before an appendix's translated title, because it reads `Section.displayTitle` in RFCKit.

**BCP 14 keywords are translated with their sentences.** Leaving every requirement in English would leave most of a protocol RFC untranslated. Implementer's bands cannot find a translated sentence by the original's words, so in a translation a requirement bands its whole paragraph, from its anchor to the next (`RequirementBands`). The header's mark says the text is a machine's. A translation is also never quoted as the RFC: Copy as Quote is off over one (`QuoteCitation`).

**Honesty.** For as long as a translation is shown, the header says "Machine-translated from English", or how far the translation is, or that it failed, with Show Original beside it (`TranslationMark`). The first translation, of RFC 2119 into German, wrote "SHALL" as "SOWIE" ("as well as").

**Kept, not redone.** Each source string's translation is kept in `Caches/RFCReader/Translations`, by document and language (`TranslationCache`). A document opened again asks the framework only for what is not kept, and a revised document only for what changed. What a batch returns is kept even when the batch fails or is canceled. A batch that ended early is no translation, and the next attempt asks for the rest.

**The whole document at once.** It is asked for in one batch, with its progress in the header, and built once. Building per section as results arrive would cost a whole build each. RFC 9110 is 2,159 strings, about 381,000 characters. Its time on the device was not measured: from a command-line tool with the screen locked, the framework answered once and then stalled. If it proves too slow, the fallback is to translate the section being read first.

Not translated, and not a goal: exports, print, citations, search, the app's chrome (the string catalogs do that), and anything that leaves the device.
