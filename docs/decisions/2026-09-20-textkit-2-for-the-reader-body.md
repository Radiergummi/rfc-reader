# TextKit 2 for the reader body

*Decided September 2026.* The reader's prose is rendered by `UITextView` / `NSTextView` with TextKit 2, not by SwiftUI `Text`. The wishlist needs link previews on hard press, hover popovers on Mac and find-in-document; SwiftUI `Text` built from an `AttributedString` handles link taps but cannot attach a per-link context menu or preview, and offers no in-document find. TextKit 2 does all of that (`textView(_:menuConfigurationFor:defaultMenu:)` and `primaryActionFor` on iOS 17+, link hover on macOS), scales to very long documents, and keeps selection across paragraphs.

`DocumentTextBuilder` is not main-actor bound. A build is string assembly, `CTLine` measurement and paragraph styles — it costs hundreds of milliseconds on the largest RFCs, and running it on the main thread is what made the font-size slider stutter. `DocumentSession` builds in an `@concurrent` function and `BuiltDocument` carries the result back; it is `@unchecked Sendable` on the strength of a handover (#128). The builder is local to `build`, so nothing that could write the text outlives the call, and every attribute value is either immutable or made by that build alone. Paragraph styles are stored as immutable copies because Foundation uniques equal attribute dictionaries across every string in the process: two builds were measured sharing 21 of RFC 8999's 47 paragraph style objects, so being unshared is not something a build can promise. There used to be a defensive copy of the finished string; it was shallow, so it protected none of this, and it cost a pass over the whole text. A handed-over build may go into more than one text view: force-click previews keep their last four builds, keyed on the document and its `ReadingStyle`, so a repeated preview is a lookup rather than a 15–55 ms build (#374). `install` copies the text but keeps the build's own attachments, so two text views then hold the same `NSTextAttachment` objects. That is sound because the kept builds live on the main actor with the text views, and because nothing a text view does writes to them, which `BuilderHandoverTests` checks by laying one build out and drawing it in two. A kept preview holds its parse beside its build, so a build is never paired with another parse of the document; and it goes when its document is removed or evicted, as the store's parse does, a preview finished after that included.

The text column is a pure function of the view's width and the measure preference (`ReaderLayout`), which is why `DocumentView` derives it rather than being told by the text view. Artwork scaling and table shape are measured against the column at *build* time, so a column that arrives after the first build means a document built against a guess and immediately thrown away; deriving it up front means one build per document instead of two, and no visible re-scroll on open.

Shape: one `NSTextContentStorage` holds the whole document body — paragraphs, lists, definition lists, artwork, tables, figures, block quotes, asides and references are all text, built by `DocumentTextBuilder` in a new `RFCReaderKit` package and laid out by a shared `RFCTextViewCoordinator` behind a macOS `NSTextView` and an iOS `UITextView`. Nothing in the body becomes a hosted SwiftUI view; the decorations attributed text cannot express on its own — the card behind artwork and tables, the rule beside a block quote, the aside tint, the reference chip — are drawn by an `NSTextLayoutFragment` subclass instead. The document header is not in the storage: it is a SwiftUI view hosted in the text view's top content inset, because it carries buttons (the status banner's links to newer RFCs) that nobody selects through. `DocumentTextBuilder` replaces `InlineText.attributedString(_:)` and the per-block SwiftUI views that fed the old `LazyVStack`; ``BuilderCompletenessTests.`nothing becomes an attachment` `` guards the "nothing becomes a hosted view" rule directly, failing on any `NSTextAttachment` outside the one chip run the design allows.

The costs that could have killed the approach — a deep jump laying out everything before it, a restyle on every font-size change, and where tables stop fitting as a grid — were measured before any of it was built, in `docs/decisions/2026-09-21-textkit-2-probe-results.md`.

Why nothing in the body is an attachment, from the design this was built from (21 September 2026): *content is text when selection matters, and a hosted view is used only where interaction matters more — and in the reader body nothing qualifies.* An attachment's view is a subview of the text view, so a drag crossing it goes to the subview and never reaches the selection machinery; the only repair is turning off its hit-testing, which takes away the very interactivity that would have justified it. Three shapes were rejected on that ground: TextKit for runs of prose with SwiftUI views between them (the cheapest, and selection stops at every view); one storage per section (selection stops at artwork and at section boundaries); and one storage with attachments for artwork and tables (holes in the storage for selection, find and VoiceOver alike). Colors are not part of `ReadingStyle` for a related reason: the storage holds dynamic colors that resolve at draw time, so dark mode or a new accent is a redraw, not a rebuild that loses the reader's place.

Artwork is therefore text: verbatim, monospaced, never wrapped, and scaled per block so its widest line fits the measure, since text has no horizontal scroll. The corpus is what made that viable rather than a fudge. Over the 8,457 converted legacy documents, 97.8% of the 404,663 artwork and source-code blocks are at most 69 columns wide and all but ten at most 79; the widest line anywhere is 129 columns (RFC 2124), which lands near half size. "Copy Figure" and ordinary selection replace the copy button the old view had. Tables are text too, so a reference in a cell is still a link and a chip, but in one of two shapes chosen by measuring the natural column widths: a **grid** of tab stops when the row fits the measure, and **stacked** — one paragraph per cell, led by its column header — when it does not. RFC tables routinely carry one prose column of 87 to 92 characters beside short ones, which tab stops can only clip or shrink; the stacked shape is also what a phone's measure needs. `LegacyTextParser` never emits a table, so nothing here reaches the legacy path.

Section tracking reads the reader's line from the layout engine (see [Decision: the reader lays out its viewport, and holds the reader's line](2026-10-01-the-reader-lays-out-its-viewport-and-holds-the-readers-line.md)), which finds it among the viewport's own fragments at the top of the visible rect, and looks up the nearest preceding anchor. Not the start of the viewport layout controller's `viewportRange`, which is deliberately larger than what is on screen and so names a section the reader has already scrolled past, and not a point lookup, which can answer a stale fragment (see "The TextKit 2 traps"). A heading a jump puts at the top reads as its own section even once the clip view rounds the offset down into the paragraph above (#299): the engine's own move, and the platform's settling of it within `AnchorKeeper.settleTolerance`, record nothing, so the place stays the heading's. The anchor index covers every anchor — sections, figures, tables, verbatim blocks and reference rows — because `scroll(to:)` must reach all of them; a missing entry is a dead link.

Original Text follows on macOS (#159): `OriginalTextBody` is a plain, read-only, unwrapped TextKit 2 `NSTextView` with a find bar, not `RFCTextView`, because none of the reader's decorations, chips or anchors apply to text shown exactly as published. It writes through `textStorage`, like the reader. On iOS it is the same kind of view (#240), a `UITextView` subclass, `SidewaysTextView`, since a `UITextView` keeps its content as wide as its frame and so clips unwrapped lines: it puts the container's size back after each layout pass, because UIKit narrows it to the frame, and widens its content size to the laid-out lines (`OriginalTextLayout.contentWidth`). The container is unbounded down: UIKit clamps a touch into the container before it finds the character under it, and a container of no height put every selection on the first line. It is a million points across rather than unbounded, because a `UITextView` takes a container 10,000,000 points wide or more as having no width and cuts the selection's highlight at the view's width, which left a selection past the right edge of an iPhone without a highlight. A non-scrolling text view inside a two-way `UIScrollView` would also have scrolled sideways, but lays out the whole RFC at once. On iOS Find is the text view's own find interaction; on macOS it reaches either text view, the reader's or this one, through `ReaderWindowController.focusSearchableText()`, which focuses the first visible text view with a find bar (`FirstResponderSearch.searchableText`) before the action goes down the responder chain.
