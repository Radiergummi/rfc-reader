# The index reads as an index

*Decided and built October 2026 (design: `docs/superpowers/specs/2026-10-05-document-index-design.md`, part 3).* An `IndexBlock` used to be set as the definition lists prep's markup is made of: a row of letter links, then each term with its locators spelled out (`Section 3.7, Paragraph 6`), a wall of links in a long appendix. The builder now sets it as an index (`DocumentTextBuilder.appendIndex`), a small letter per group, a line per term with its locators shortened to `§3.7 ¶6`, the primary first and semibold, subentries one step in. Three overlays drawn over the reader help find a place in it: the current group's letter pinned at the top, an A–Z rail in the trailing gutter, and type-select.

**No filter and no sort in the body.** ⌘F already searches the whole document, and an index is in alphabetical order by definition; a filter that hid entries would make the body a second, worse search, and a sort would undo what the index is (the maintainer's call, 5 October 2026). Type-select is the one way of typing to it, as one types to a list in the Finder.

**Locators keep their paragraph.** RFC 9114 cites paragraphs, not sections: 21 of its 32 entries cite one section at several paragraphs, one entry up to 40 times (counted over `corpus/xml.noindex`, 5 October 2026). Cut to the section, those entries read `§4.1 §4.1 §4.1`. A label keeps `¶N`; an item level (`, Item 2`) is left off the label, since a paragraph is fine enough to find it, but the link still leads to the item. A label of any other shape, `Table 2`, is prep's, unchanged (`IndexLocatorLabel`).

**Type-select reads the top-level entries only.** Subentries are sorted under their heading entry (`Grammar` → `ALPHA`), not across the index, so mixed into the order they would break the fallback that lands an unmatched prefix on the entry where it would sort.

**The overlays are platform views over the scroll view, not a SwiftUI overlay, and nothing inside the text.** The pinned letter moves with every scroll frame: an overlay fed through SwiftUI's observation would trail the text by a frame and invalidate SwiftUI on every tick, and every position is in the text view's coordinates. So the coordinator places a label and a small rail view (`IndexOverlayController`, `IndexRailView`) on each viewport report, the same report that drives the toolbar's running heading, and every decision they show (whether the index is on screen outside folded text, the current group, the push-out, the rail's rows and hit-testing, the match) is a pure function in RFCReaderKit (`IndexOverlay.swift`), under test. On macOS the pinned letter is a subview of the scroll view above its clip view, not a floating subview (`addFloatingSubview`), which the design had named: the push-out moves it on scroll anyway, and the rail is placed in the same coordinates. A preview's reader, printing and the PDF export show the layout without overlays.

**Two things only a run in the Simulator showed**, both now pinned: a jump puts a group's label at the top to within a rounding error, 0.013 points above it, which counted as scrolled past and pinned a second copy over the label (`StickyLetter.tolerance`); and under viewport layout a label's fragment can be found before it is laid out, its frame still at the top of the document, which gave a wild push-out, so only fragments whose layout is available are measured.
