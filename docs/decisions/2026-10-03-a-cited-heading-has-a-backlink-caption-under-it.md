# A cited heading has a backlink caption under it

*Decided October 2026 (issue #584), replacing how [the backlinks decision](2026-09-30-a-heading-lists-the-sections-that-refer-to-it-through-a-chip.md) showed them.* The chip at the end of a heading, `↩ 3` in the accent color at the heading's size, read as part of the heading and drew more attention than the heading itself. Nearly every heading in a large RFC has one, so the effect repeated all the way down the document. A cited section now has a caption under its heading instead: an arrow (`arrow.down.backward`, Notion's backlinks arrow) and the count, "One Backlink", "Two Backlinks", "Three Backlinks", then "4 Backlinks" in figures (`DocumentTextBuilder.backlinksCaption(count:)`). The count is of citing sections, not of citations. It is set in the caption font and the secondary color, as the title block's detail lines are. What is counted, the list it opens and how the list behaves are unchanged.

It is a paragraph of its own, not a line of the heading's paragraph, for three reasons. The running heading measures a heading's last line to hand over (`RunningHeading.crossing`), and a line inside the paragraph would delay the hand-over to the caption. A jump keys on the heading's anchor offset, which does not move. And the headings rotor sees the heading alone, as one stop. The heading keeps only a hairline of space after it, and the caption takes the heading's usual gap, so a cited section grows by about one caption line.

Every character of the caption carries `.rfcBacklinks`, its line break included, so a copied heading and its body have no line where the caption was. Its words and arrow carry the `rfc-backlinks:` link and `.rfcSpoken`, the caption's own words, so VoiceOver on macOS reads "Three Backlinks" and not the arrow. On iOS, which has no per-range accessor to override, the words are now in the text for VoiceOver to read, not a bare number. `backlinkCaption(at:)` gives the caption's extent without its line break, which is where the list is anchored. The arrow is the one attachment outside a chip's run that the completeness guard admits, and only inside an `.rfcBacklinks` run; it is drawn, sized and centered as a chip's symbol is, in the secondary color.

A text view draws a link in its own link color, over the color the storage gives it, so the caption would be accent-colored however it was built. The coordinator is the layout manager's delegate, and `textLayoutManager(_:renderingAttributesForLink:at:defaultAttributes:)` hands the decision to `DocumentTextBuilder.linkRenderingAttributes(for:defaults:)`. That function drops the foreground color for a backlinks link alone, so the caption keeps its own color. A trap: once the delegate answers this, TextKit stops reading the text view's `linkTextAttributes`. Its `defaultAttributes`, and a `nil` answer, are TextKit's own, which are blue and underlined. Passing them through underlined every link in the document, as the first build of this change found on screen. So the delegate starts from the text view's own attributes, kept by the coordinator behind a `Mutex` because TextKit may ask off the main thread. On macOS that is a copy of `linkTextAttributes`, taken once the view is configured: `linkColor`, without the underline the reader removes. On iOS `linkTextAttributes` is only the view's tint, the color as it was when read; measured in the Simulator, it was the same `systemBlueColor` as `tintColor`, where TextKit's default is `linkColor` and underlined. So on iOS the delegate starts from the dynamic `.tintColor` instead, which follows the view's tint as UIKit's own link coloring does. Every other link is drawn as before.
