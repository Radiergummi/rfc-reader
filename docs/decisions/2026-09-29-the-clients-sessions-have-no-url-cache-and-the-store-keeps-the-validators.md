# The client's sessions have no URL cache, and the store keeps the validators

*Decided 29 September 2026 (issue #314, pull request #409).* `RFCEditorClient` fetched through `URLSession.shared`, whose `URLCache` kept a second copy of what the app already keeps. Every body the client fetches has an owner: a document is written by `DocumentStore`, and the index is kept beside its snapshot. RFCs do not change once published, so the cached copy of a document was only disk. The client's default transport is now `URLSessionTransport` over `URLSession.rfcEditor`, whose configuration has no `URLCache`.

The index is the one body that changes, and its revalidation is the store's, not the session's. The index refresh sends the kept `ETag` (and `Last-Modified`, which the RFC Editor does not send today) as `CacheValidators`, and a `304` only records the check. What the store keeps for it is `IndexCheck` in `RFCReaderKit`, `rfc-index-check.json` beside the index: when the index was last checked, when it was downloaded, and its validators. The validators are sent for `IndexCheck.validatorLifetime`, a week after the download, and then dropped, so the next check fetches the whole index. The server's only validator is its `ETag`, and a tag that stayed the same while the index changed would otherwise answer `304` forever while the list said it was current. With a `URLCache` in the session, its own revalidation would stand between the check and the `304` the check asks for.

The automatic daily check nobody is waiting for goes through a second session, `URLSession.rfcEditorOnCheapNetworks`: also without a `URLCache`, it disallows expensive and constrained paths and sets `waitsForConnectivity`, so on cellular, a hotspot or Low Data Mode the check waits for a path it may use instead of failing. Retry and pull to refresh use `URLSession.rfcEditor`, take any network and fail fast.

The cost is the small bodies that had nothing else keeping them. The Just Published feed (`rfcrss.xml`) and the metadata JSON lose the free revalidation the shared cache gave them: the feed is about 4 KB compressed, measured, fetched whole at each launch. In return documents are not stored twice, and nothing stands between the index check and its `304`.
